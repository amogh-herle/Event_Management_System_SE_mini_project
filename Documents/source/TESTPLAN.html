1. Introduction

Purpose: defines the test plan for EMS v1.0 — objectives, scope, strategy, environment, schedule, responsibilities, and the functional, non-functional and security test cases with their results.

Scope: all 20 functional requirements (FR-001a – FR-010b), all 7 non-functional requirements (NFR-001 – NFR-007) and the security requirements SR-001 – SR-012. Third-party services (PostgreSQL engine, SMTP provider, Vercel) are not re-tested.

References: SRS v3.0, SAD v3.0, SRSec, tests/*.test.ts, scripts/test_fr*.ts, .github/workflows/ci.yml, docs/reports/*.

Definitions: UT/IT/ST = unit/integration/system test; SEC = security validation case; NFT = non-functional test; RTM = requirements traceability matrix; “live” = executed against a running production build of main.

3.1 Security features

Security reqFeatureTest case(s)
SR-001Passwords shall be stored only as salted bcrypt/Argon2 hashes and never logged.SEC_01
SR-002Session cookies shall be HttpOnly, SameSite and Secure (production), HMAC-signed, and shall expire after 30 minutes of inactivity.SEC_02, SEC_11
SR-003The account shall lock after 5 consecutive failed login attempts.SEC_03
SR-004RBAC and least privilege shall be enforced on the server for every request; no client-supplied role claim shall be trusted.SEC_04, SEC_13
SR-005Object references shall be authorized server-side (ownership checks) to prevent IDOR.SEC_05
SR-006All client-server traffic shall use TLS 1.2 or higher.SEC_06
SR-007Sensitive data at rest shall be encrypted.SEC_06
SR-008All database access shall use parameterized queries / an ORM.SEC_07
SR-009User-supplied input shall be validated and output encoded to prevent XSS.SEC_08, SEC_15
SR-010State-changing requests shall be protected against CSRF.SEC_09
SR-011Security events and administrative actions shall be recorded in a durable audit log (12 months) without secrets or plain-text passwords.SEC_10
SR-012Verification and reset tokens shall be random, single-use, time-limited and stored hashed; login errors shall not reveal whether an account exists.SEC_12, SEC_14

4. Features not to be Tested

  • PostgreSQL engine internals, the SMTP provider's delivery and the hosting platform's internals (assumed correct; EMS's own use of them is tested).
  • TLS configuration and storage encryption of the hosting platform — not independently scannable locally (SEC_06 recorded “Not run”).
  • Cross-browser rendering on Safari and Edge, and the first-time-user usability study (needs real participants/devices) — recorded as not executed in NFT_08.
  • Native mobile apps, payments and external calendar integration (out of scope in the SRS).
  • Production uptime (99.5%) — needs a month of monitoring.

5. Test Approach / Strategy

Levels

LevelID prefixWhat it exercisesTooling
UnitUT_A single function/validation rule in isolationnode:test (tsx), in-memory/mocked Prisma where noted
IntegrationIT_A route + business logic + real PostgreSQLnode:test against Postgres (CI service container)
SystemST_A user-facing flow across requests/rolesnode:test route handlers; live scripts against a running production build; manual UI walkthrough where noted
Acceptance—SRS acceptance criteria and exit criteriaThis plan §14

Types

  • Functional (60 FR cases, §5.2) · Regression (270 automated tests on every push/PR) · Performance/concurrency (§5.3) · Security (§5.1) · Accessibility (axe-core) · Recovery drill (pg_dump/pg_restore)

Entry criteria: stable build on main, test database available, test data seeded. Exit criteria: 100% of planned cases executed or explicitly recorded as not run with reason; all High-priority FRs pass; every failed or partial case has a documented deviation (SAD 4.6).

11. Assumptions & Dependencies

  • PostgreSQL 16 and Node are available to run the suite; CI service container is healthy.
  • Test accounts and data are generated per run; no production data is used.
  • SMTP is replaced by jsonTransport in tests.
  • Hosting platform provides TLS and storage encryption as documented.

12. Suspension & Resumption Criteria

Suspend if the CI pipeline or Postgres service cannot start (blocks all IT_/ST_ cases), or the build is too unstable (blocks >30% of cases). Resume when the blocking defect or environment issue is fixed; previously passing cases are re-run only if the fix touched code they exercise.
